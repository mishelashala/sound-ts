Authoring — string literal brands

Prefer .sts files. Stock TypeScript language service will red-squiggle brand type inside ordinary .ts / .tsx. The VS Code TextMate grammar covers .sts; injection into .ts only helps highlighting, not the checker. 

// file: roles.sts
brand type Account = "admin" | "regular";

function greet(role: Account): string {
  return role === "admin" ? "hello, admin" : "hello";
}

// After CLI transform, Account is also a runtime companion:
greet(Account.from("admin"));
Account.is("guest");   // false
Account.from("guest"); // throws

Refined brands

Emit keeps type Name = base; under stock tsc the refinement is runtime-only (.is / .from) — expected.

Custom is body; CLI generates from that validates via is. Emit is plain .ts (type alias + companion) — expand, then stock tsc. 

// file: positive.sts
brand type PositiveInt = number {
  is(n: number): n is PositiveInt {
    return Number.isInteger(n) && n > 0;
  }
}

Emit shape (plain TS after transform):

type PositiveInt = number;
const PositiveInt = /*#__PURE__*/ (() => {
  function is(n: number): n is PositiveInt {
    return Number.isInteger(n) && n > 0;
  }
  function from(value: unknown): PositiveInt {
    if (is(value as number)) return value as PositiveInt;
    throw new Error(/* … */);
  }
  return Object.freeze({ name: "PositiveInt" as const, is, from });
})();

Brand-only unions / intersections

Members must be known brand names from the transform input — same file or another .sts on the CLI batch. Open types like string in a brand | / & are rejected; unknown brands and cycles error at transform time.

Two-file example (declare in a.sts, compose in b.sts):

// a.sts
brand type Admin = "admin";
brand type Regular = "regular";

export { Admin, Regular };
// b.sts
import { Admin, Regular } from "./a.js";

brand type Staff = Admin | Regular;

Run sts on the directory (or both files) so the project brand map sees every declaration, then point stock tsc at the expanded output.

Union emit delegates .is to members:

type Staff = Admin | Regular;
const Staff = /*#__PURE__*/ (() => {
  function is(value: unknown): value is Staff {
    return Admin.is(value) || Regular.is(value);
  }
  function from(value: unknown): Staff {
    if (is(value)) return value;
    throw new Error(/* … */);
  }
  return Object.freeze({ name: "Staff" as const, is, from });
})();

Call-site usage of the runtime companions:

Staff.is("admin");     // true (Admin member)
Staff.from(raw);       // throws if neither brand matches

Same-file intersections still work:

brand type User = "u";
brand type Session = "s";
brand type Authed = User & Session;
// Authed.is(value) → User.is(value) && Session.is(value)

validate type

Object types with primitive fields expand to the same .is / .from companion shape as brands. Stock tsc sees a plain type alias + runtime object. 

// file: user.sts
validate type User = { id: string; age: number };

User.is(data);   // boolean
User.from(data); // throws on mismatch

Supported field shapes:

  • string | number | boolean
  • optional ?
  • arrays of those primitives (string[])
  • unions of those (string | number, string[] | number)

Unsupported shapes (nested objects, generics, Date, imported aliases as field types, …) error clearly at transform time — not a full schema library. 

validate type Flags = {
  active?: boolean;
  tags: string[];
  id: string | number;
};

Checked casts — as!

Throw-on-mismatch cast. Targets are primitives or known companions (brand type / validate type) from the CLI batch. 

const n = raw as! number;
// → inline typeof check; throws if not a number

const u = raw as! User;
// → User.from(raw) when User is in the project companion map

Unknown targets error at transform time. Pass the whole .sts batch so cross-file as! User resolves.

Adoption recipe (not all-or-nothing)

Keep most of the app as normal .ts (stock tsc / Vite). Add .sts only where you want brand type, validate type, or as!.

Two-step compilation (expand, then stock build):

.sts  --sts -o …-->  plain .ts  --tsc/nest-->  .js in normal build out
  • sts never emits .js
  • Default dir → dir.out/ or -o you choose (e.g. src/brands.generated/)
  • Stock Nest / tsc still owns dist/
  • Don’t point tsc at raw .sts
  • Whole .sts batch on each sts run for cross-file | / & and as! companions
  • Start with one leaf brand file (ids / roles) → grow file by file

Caveats

  • Parser edges: regex literals; nested ${} in templates (whole template skipped).
  • Editor: author in .sts to avoid stock tsc red squiggles on the dialect keywords.
  • Cross-file companions: pass every .sts on the CLI batch (e.g. a directory) so | / & members and as! targets resolve against the project companion map. After expand, stock tsc sees normal imports of the emitted type + companion.

defineLiteralSet?

Internal emit / runtime helper — not the public API. Authors write brand type; the CLI expands. Do not treat import { defineLiteralSet } as the product.

Non-goals (this cut)

  • No Microsoft / TypeScript fork to maintain
  • No custom TypeScript checker or language server — stock tsc runs on expand output only.
  • No open brands without is (use refined brands; later tip for phantom ID opacity + .from — not open-without-is)
  • String literal brands are structural under stock tsc (not nominal). Number/bigint literal brands not supported yet.
  • Not a full schema library — validate type covers simple object shapes only (no nested objects, generics, Date, …)
  • VS Code extension not on Marketplace yet (local install only)
  • defineLiteralSet is not the authoring surface

FAQ: Why not TypeScript?

TypeScript’s design non-goal: don’t add RTTI or emit different JS from the type system — no runtime overhead from the type layer.

Features declined / left out for that reason (buckets, not a full issue archive):

  1. Runtime validation from types (auto .is / assert)
    This dialect covers it via validate type — see Validate type. 
    validate type User = { id: string; age: number };
User.is(data);   // ✅ companion
User.from(data); // throws on mismatch
  2. Nominal / opaque / brand types with runtime companions
    That’s what brand type + companions cover here — see CLI quickstart / String literal brands.
  3. Reified generics 
    function empty<T>(): T[] { return []; }
empty<string>().$type; // ❌ T is gone at runtime
  4. Pattern matching / runtime exhaustiveness from unions 
    match(status) {
  "ok" => 1,
  "err" => 0,
} // ❌ no emit; switch + `never` check is manual
  5. Traits / typeclasses as runtime dispatch 
    trait Show<T> { show(t: T): string }
show(42); // ❌ no runtime method table from the trait
  6. Contracts / checked casts
    This dialect covers it via as! — see Checked casts. 
    const n = raw as! number; // ✅ throws on mismatch
const u = raw as! User;   // ✅ User.from when companion is in the batch
  7. Serialization codecs from types 
    type Dto = { email: string };
JSON.parse(s) as Dto; // ❌ no auto encode/decode / schema from Dto
  8. Dependent / refinement types with runtime proofs without user is 
    type PositiveInt = number & { _brand: "pos" }; // type-only
PositiveInt.from(-1); // ❌ TS won’t generate the check for you

TS already emits for some expression features (enum, namespace, parameter properties, downleveled class/async, decorators) — those aren’t “types that generate companions.”

Bottom line: if the value is erase-the-type and emit a runtime artifact from it, TS usually says no — libraries / transformers / sts fill that gap.
